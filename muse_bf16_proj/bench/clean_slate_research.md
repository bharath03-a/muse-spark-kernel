## 1. Multicast the weights across token partitions

This differs from the disproved x-ingress proposal. Current pooler256 `_big_gemm` has BM64 tokens, BN128 output rows: four token tiles request the same weight matrix. Original W is67.1MB; total requested W payload is268.4MB, though L2 can satisfy repeats. Current profile time27.15us leaves9.78us above its compute bound. Unpooler256 takes24.67us. One cannot infer268MB HBM traffic from these shapes.

Cluster peers can own disjoint token ranges for the SAME output rows. They receive one multicast W tile and private x tiles; there is no split-K and no output reduction. At BN64,128 tokens/CTA,cluster2, pooler256 has64 clusters/128 CTAs; unpooler256 has128 clusters/256 CTAs. Accumulator is64 FP32/thread. Four stages,BK128 use~192KiB shared/CTA. At m128,64 tokens/CTA gives32 acc registers and~128KiB shared. The default m256 configuration therefore supports only one resident CTA/SM by shared memory; its128-CTA grid can still cover132 SMs.

R17 does NOT reject this: `R17_INST` uses cluster(2,1) exclusively with swapped GEMM `W[n,k] @ x[m,k]^T`; that shares x across output rows. Weight sharing here is cluster(1,2) in that notation. The same distinction applies to r13 o multicast.

Cost model: eliminating one repeated67MB weight request could save roughly6.7us if it were charged at10TB/s marginal L2 ingress, or14us if charged at4.8TB/s HBM. Both are ceilings, not additive gains: multicast delivery still costs resources and the kernel has a compute floor. If L2 is already near-perfect and not limiting, benefit may be zero. A >=0.5us gain is plausible on large-m pooler/unpooler but unproven.

`clean_slate_weight_multicast.py` implements a conservative runnable hypothesis using pinned3.8 Gluon APIs. `run(...multicast=False)` is the identical-layout/schedule control. The cross-CTA barrier before each reused stage is essential: local WGMMA retirement does not establish peer retirement. It may erase the benefit. A faster implementation needs per-stage peer consumer credits, not simply deletion of barriers.

Smallest future experiment: compile both for pooler256; inspect `num_ctas=2`, `n_regs/n_spills/shared`, PTX multicast mask, and private x offsets. Verify FP64/random/outlier/onehot, changed input, >=20 identical replays, m128/256. Pair MC/unicast using cold graph replay, then compare the winning absolute time against current canonical. Record bytes from profiler if available. Stop if MC-unicast difference is <0.5us or MC loses canonical. A slow conservative ring rejects that implementation, not all faster credit protocols.

## 2. Share a weight stage between token-specialized consumer warpgroups

Alternative to inter-CTA multicast: one CTA has two consumer WGs, each computing64 output rows ×128 DIFFERENT tokens, with one W stage and two private x stages. For m256 this requests W once per output tile. Current r9's NWG partition instead grows W rows (`BN=64*NWG`), so it does not implement this mapping. Existing generic CUTLASS failures do not isolate it.

The important restriction is occupancy:64 output CTAs on pooler underfill132 SMs. Use split-K2 to recover128 CTAs, with deterministic fixed-order reduction, or initially test unpooler whose128 output CTAs already fill the device. Token-partitioned two-WG CTA gives64 accumulator registers per consumer thread instead of128 in one WG computing256 tokens. W stage bytes remain16KiB atBK128; x stages total64KiB. A4-stage ring would be320KiB and is impossible; BK64 +4stages is160KiB plus barriers/epilogue. This resource calculation rules out a naive copy of the current8-stage ring.

Minimal test: unpooler256 only, BN64,BT128 perWG,BK64,stages3/4,8 consumer warps; two independent accumulation chains, shared W tile. Compare to an equal-resource two-WG control with W duplicated. No split-K initially. Hypothetical saving0.5–2us is possible from reduced W requests and accumulator/register pressure, but64/128 active SM distribution and WGMMA issue serialization may lose. Reject on spills, lower occupancy, or no absolute canonical gain. This is more implementation work than idea1 and has no ready code here.

## Why only two proposals survive this audit

Dense BN32 mma_v2, generic persistence, router stacking/distributed reduction, x multicast, zip block-size tuning, and the original compression-in-register concept are already tested or already implemented. A new lossless codec needs an actual bytes/exception study before a performance proposal; repeating it here would create the appearance of novelty. Neither of the two surviving architectures establishes top50, and their benefits overlap through the same weight reuse mechanism.

## Second-architecture feasibility amendment

`clean_slate_token_warpgroups.py` is now a concrete isolated8-warp source probe. It uses `NVMMADistributedLayout([3,0], [4,2], [16,128,16])`, logical accumulator `[64,256]`, one shared W tile `[64,64]`, and shared x tile `[256,64]`. The two WG-N partitions receive different128-token ranges and the same W rows. Pinned3.8 `test_tma_mma_shared_inputs` explicitly includes Hopper `[4,2]` warp layouts; that is source evidence for layout support, not compilation evidence for this specific ring. BN32 is excluded: physical Hopper WGMMA M is64, and feeding a32-row shared tile is unsafe unless padded; padding also loses the proposed efficiency.

For unpooler256, N8192/BN64 gives128 CTAs, sufficient to cover most132 SMs without split-K. Four BK64 stages consume160KiB/CTA plus32 barrier bytes. The accumulator needs64 FP32 registers per consumer thread; actual registers/spills must be inspected. The4-warp `token_tile=128` control uses two token tiles,256 CTAs,96KiB shared/CTA, and requests W twice. The8-warp path requests W once. Both controls deliberately use the same local CTA barrier after `wait_group1`: each WG independently retires its own operations, so one elected leader cannot reuse a stage until both WGs retire it. A CTA barrier is needed here even though no inter-CTA multicast exists. It may still erase the gain.

An explicit producer plus two independent4-warp consumers is also expressible through `gl.warp_specialize`: launch `num_warps=4`, with default consumer0 and additional workers `[consumer1,producer]` sized `[4,1]`. Each consumer uses its own `[64,128]` accumulator and a different128-row slice of x. Both wait on the same ready barrier; each contributes one arrival to a stage-empty barrier initialized with count2, after its WG retires the previous stage. Producer waits until both arrivals before overwriting W. Consumers must store their own outputs within their partition because worker partitions cannot return tensors. Physical warps round up to12, not8; a proposed register budget must account for that rounding. This approach replaces per-iteration CTA rendezvous with explicit credits but is more code than the direct8-warp diagnostic.

Next gate: compile the8-warp and4-warp probes, inspect shared usage, spills, and distinct B descriptor offsets between WGs with identical A offsets. Then correctness and paired cold graph timings against canonical unpooler256. No new GPU work was performed. The amended source passes CPU syntax only.

Primary sources: [Hopper MMA layout tests](https://github.com/triton-lang/triton/blob/v3.8.0/python/test/gluon/test_core.py), [warp_specialize contract](https://github.com/triton-lang/triton/blob/v3.8.0/python/triton/experimental/gluon/language/_core.py), [partition/register allocation tutorial](https://github.com/triton-lang/triton/blob/v3.8.0/python/tutorials/gluon/08-warp-specialization.py).

## Requested compressed register-A WGMMA audit

The requested mechanism is legal but already exists in `bench/zip_gluon_dev.py`, rather than being a new idea. `zgemv`'s `MMA==3` branch calls `_raw` to load packed planes, `_finish` to decode into registers, asserts a trivial conversion into `DotOperandLayout(0,mma,k_width=2)`, and supplies each decoded tensor as WGMMA A while x remains shared B. No BF16 decoded-W shared-memory round trip appears in that source path. `sweep_zip_gluon.py` lists seven MMA3 configurations, including Q1/KG1/S8 and Q1/KG2/S5 plus K-folded alternatives. No corresponding saved stdout, PTX, or numerical/timing result was found in the workspace. Thus 'already implemented' is proven; 'this exact path measured0.6–0.75x' is not established by available artifacts.

The [NVIDIA WGMMA register-fragment contract](https://docs.nvidia.com/cuda/parallel-thread-execution/) permits BF16 register A with four packed32-bit registers per thread for each m64k16 fragment, eight BF16 values. Dense n8,n16,n32 are legal, so m1 can pad to8 and m8/16/32 need no mandatory n64 padding. A is register-fragment ordered; B uses the shared descriptor layout. [Pinned Gluon API](https://github.com/triton-lang/triton/blob/v3.8.0/python/triton/experimental/gluon/language/nvidia/hopper/__init__.py) accepts tensor A and shared B. These contracts establish expressibility, not a timing result.

The format matches current12-bit semantics but not its physical byte arrangement: current zip has64-K units and per-warp fragment packing; this older Gluon source uses128-K groups with two64-K halves, register-order packed planes and padded per-block escape lists. It needs its own lossless untimed re-encode; the current packed buffer cannot simply be reinterpreted. The exact same mathematical precision and escape preservation must still pass FP64/probe tests.

The strongest opportunity is pooler/unpooler m32, currently uncompressed. Saving16.8MB weight payload has a3.5us HBM ceiling at4.8TB/s; it is not a forecast. RSWGMMA can reduce MMA instruction issue count versus per-warp m16n8 mma.sync when tokens grow to32, while decoding the same bytes. Register pressure, RS issue/dependency fences, shared compressed-plane loads, escape correction,64-CTA occupancy and pipeline retirement can consume the entire saving. Already-compressed m1/m8 are within~0.6us combined decode/compute/epilogue cost, so a large gain there is unlikely from replacing only MMA.

`clean_slate_rs_decode_probe.py` wraps the EXISTING implementation into one compressed and one dense twin with exact Q1/KG1/S8/warps4 geometry. It is a provenance/audit aid, not an innovative kernel. Next authorized experiment should inspect actual PTX A register operands, confirm no mainloop decoded-W stores, distinguish escape-fix shared activity, then compare compressed/dense/current canonical under the same cold graph harness. Preserve raw output so this hypothesis is not recycled again without evidence. CPU syntax passed; no GPU work occurred.

## Adaptive-record peer review and intra-CTA K split

Reviewed collaborators' `adaptive_record_codec.py` and `adaptive_record_kernel.py`. The first byte-gather prototype was mathematically consistent but packed physical cp14 lane order differed from its DotA distributed layout, risking poor vectorization. Compiler peer replaced it with `dot_record_order()` matching standard DotA lane bases, explicit16-byte vector loads, and predicated raw/compressed selection. The current pack32 ASM outputs16 32-bit registers representing32 BF16 values; inputs are32 pointer operands followed by32 flags, so operands$16 and$48 are correct. Pointer/flag are constant over each thread's register fragment. All16 outputs are assigned on each predicate path. CPU mapping evidence is supplied by collaborators; GPU compilation remains unverified.

Use pooler/unpooler m32 first: they currently use dense W. Adaptive records with13% raw blocks have~4.6% extra traffic versus12-bit zip but still~21.5% less than BF16. Removing sparse correction is a format simplification, not an established speedup over current z9's parallel correction warp: its measured no-fix ablation barely changed m1/m16 timing.

Root proposed restoring z9's intra-CTA K split rather than assigning all four warps separate output rows over fullK. This is source-supported by pinned Triton: [getMmaV2WarpsPerCTA](https://github.com/triton-lang/triton/blob/v3.8.0/lib/Dialect/TritonGPU/IR/Dialect.cpp) chooses batch-axis warps for rank3; [MMAv2 lowering](https://github.com/triton-lang/triton/blob/v3.8.0/third_party/nvidia/lib/TritonNVIDIAGPUToLLVM/DotOpToLLVM/MMAv2.cpp) explicitly lowers batch repetitions. Proposed logical accumulator is `[W,R,M]`, A`[W,R,64]`, B`[W,64,M]`, with warps_per_cta`[W,1,1]`; each batch is one warp and owns a distinctK/W range. Rank3 instruction tile should be`[1,16,8]`, consistent with the rank3 tile conversion contract, but this exact Gluon construction needs compilation. Extend existing DotA register/lane bases by a leading zero and map warp bases to batch instead of output rows. No CTA synchronization is needed inside the direct-LDG + synchronous MMA2 loop.

For R32,W4, pooler gets128 CTAs and32 iterations/warp atK8192, unpooler gets256 CTAs and16 iterations atK4096. Accumulator needs16 FP32/thread at m16 and32 at m32. `gl.sum(acc,axis=0)` performs one deterministic FP32 inter-warp reduction at the end; apply scale afterward and cast toBF16 once. R16 gives twice the CTAs and half the accumulator, but doubles x requests again. R32 doubles x requests versus the current naiveR64 fullK prototype (~33.5→67MB for pooler m32), so increased occupancy is not free. Actual timings must decide whether shorter critical loops outweigh reduction and ingress.

Bounded multicast-credit investigation found no safe shortcut: exposed pinned `mbarrier.arrive` has no peer-CTA argument, and slicing a shared descriptor preserves its layout rather than proving ownership redistribution. A `.slice(...CTA0...)` call does not establish valid remote arrivals. Register-source async-store completion could implement credits, but destination/barrier ownership and owner-only waits need an isolated protocol proof. No multicast-credit implementation was added.

Final source review of `adaptive_record_split_kernel.py` found no mismatch. Pinned `LinearLayoutConversions.cpp` requires rank3 Ampere instruction tile shape; `[1,16,8]` gives instrM16 through indexrank−2. DotA's native register bases K0,row8,K8 extend in K-major order withK16,K32, thenrow16, matching the supplied DLL. Batch/row/K nested SliceLayouts are expanded in the inverse slicing order. Weight record units and x positions both select the same warp's K/4 partition. Final FP32 sum returns `SliceLayout(0,mma)`, matching output index layouts; scaling and BF16 cast occur afterward.

Independently ran system-Python `adaptive_record_split_kernel.py --syntax` and `adaptive_record_split_mapping_test.py`: both pass. The latter covers4096 mixed compressed/raw decoded values, all weights exactly once for N64/K512, uniform pack32 pointer/flag groups, and exact integer four-wayK partition sums. This verifies CPU addressing/arithmetic reasoning, not Triton compiler lowering, GPU numerical behavior, or performance.

## Measured adaptive losses and next causal experiment

Parent's actual judge preparation timings rejected both adaptive paths. Direct m32: pooler318.72us versus22.40us canonical; unpooler162.18us versus21.86us. Intra-CTA K split:109.34us versus21.89us and58.24us versus21.50us. Both selected nothing. Correctness passing does not make these performance candidates. These are same-run raw cold-graph comparisons; no graph-overhead subtraction is needed to identify the losses.

Offline split PTX has no shared stores/barriers inside the hotloop, but synchronously loads metadata, uses it to form payload pointers, loads/decodes two records, then loads32 scalar packed x operands before MMA. There is no cross-iteration prefetch. This establishes a dependency chain; it does not prove how many measured cycles each component costs. A direct-versus-split speed ratio also changes CTA geometry, so it cannot establish a causal memory-latency diagnosis by itself. The31 epilogue barriers are an avoidable cost, but an epilogue-only change is not credible as the solution to an~90us gap.

A materially different, source-supported experiment is a compressed-byte `cp.async` ring. Pinned [Gluon Ampere async_copy](https://github.com/triton-lang/triton/blob/v3.8.0/python/triton/experimental/gluon/language/nvidia/ampere/async_copy.py) exposes masked `async_load`, `commit_group`, and constant `wait_group`; [NVIDIA PTX](https://docs.nvidia.com/cuda/parallel-thread-execution/) permits these operations onSM80+, includingHopper. W4/R32 needs eight fixed2048-byte slots per stage; depth4 costs64KiB. A physical `[8,512]` uint32 stage with BlockedLayout`([1,4],[1,32],[4,1],[1,0])` gives each lane one16-byte segment per plane. Warp b owns records b andb+4. Predicating the fourth plane for compressed1536-byte records preserves compressed traffic; all records keep identical destination slot addresses.

If shared loads preserve that same physical lane mapping, a lane consumes only bytes it copied. Per-thread `wait_group(3)` is then sufficient before reading its own ready slot, without a CTA rendezvous. Prefill four committed groups; commit one future group every iteration, including masked empty tail groups, to retain fixed group indexing. Load the current slot fully into registers before overwriting it for iterationi+4. Decode register values, perform synchronous MMA2, and drain with `wait_group(0)` before exit. This keeps exact raw/packed selection, removes neither precision nor timed work, and introduces no decoded-W shared store or CSR correction.

The ring still has synchronous future-metadata reads and direct x loads. It is therefore a test of weight prefetch, not a promised complete latency fix. Adding x staging would make a128KiB depth4 ring at m32/W4, but x reads usually need data from other lanes; [NVIDIA warp synchronization guidance](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/cpp-language-extensions.html) then requires a warp-level sharing fence after per-thread async waits. Do not infer cross-lane visibility from a thread's own wait alone. No new GPU work was performed by this agent.
